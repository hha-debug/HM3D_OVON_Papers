# OmniNav Method

```text
OmniNav Method
├── ① 多模态统一编码：怎样用一套模型接收不同导航目标？
│   ├── 文本：路线指令、目标物体类别、点目标描述 → 文本 tokens
│   ├── 坐标：子目标或候选 frontier 的平面坐标与朝向 → MLP → 坐标 tokens
│   └── 图像：当前观测与时空采样的历史图像 → ViT → 图像 tokens → 共享 Qwen2.5-VL-3B
│
├── ② 快系统：怎样把任务与视觉理解变成连续移动？
│   ├── 条件融合：VLM 融合图像、文本及任务需要的坐标 → 作为策略头的条件特征
│   ├── 航点生成：DiT 变体 + Flow Matching → 联合预测未来 5 个连续航点及到达标志
│   └── 闭环执行：执行近期航点 → 接收新图像 → 重新预测；快系统本身可以独立完成导航
│
├── ③ 慢系统：怎样利用历史与探索前沿选择下一处目标？
│   ├── 空间记忆：维护带位姿的历史图像及占据地图 → 提取已探索与未知区域之间的 frontiers
│   ├── 全局决策：目标出现于当前或历史观测 → 预测目标坐标；尚未找到 → 推理并选择探索子目标
│   └── 分层协作：慢系统输出子目标 → 转为 Point-goal → 快系统依靠视觉生成局部航点；两者共享 VLM 参数
│
└── ④ 离散与连续两阶段训练：怎样兼顾语义能力与导航控制？
    ├── 第一阶段：离散动作、视觉语言、具身问答与定位数据 → 自回归监督，建立语义与动作对齐
    ├── 第二阶段：接入 Flow Matching 策略头 → 用示范轨迹监督连续航点，坐标做 min-max 归一化
    └── 能力保持：继续混入第一阶段离散数据的 20% → 联合训练，保留语言、物体与空间关系理解
```

**主要贡献：**围绕 Qwen2.5-VL-3B-Instruct 构建统一导航框架，支持 Instruction-goal、Object-goal、Point-goal 以及前沿探索。核心设计包括：将坐标作为额外模态与图像、文字共同编码；在 VLM 后接 Flow Matching 策略头，生成连续航点；用共享 VLM 的快慢系统衔接全局子目标选择与局部视觉导航；通过通用视觉语言、目标定位和导航数据联合训练增强泛化。快系统可以独立运行，慢系统用于增强长程探索与历史信息利用。其具体贡献在于这些部件在导航任务中的组合与验证，Flow Matching、DiT、KV cache 和 frontier 本身均是已有技术。依据见 §1、§3、Fig. 1。

**输入：**按任务接收自然语言路线指令、目标物体类别或点目标坐标，以及当前与历史 RGB 图像。坐标经 MLP 映射成稠密向量；图像由 ViT 编码后，与文本共同输入 VLM。论文主表的纯视觉快系统采用左、前、右三视角 RGB，历史缓冲主要保存前视图像。完整快慢系统还使用深度与里程计辅助构建、维护占据地图并定位候选前沿，Table 2 明确列出 Depth 和 Odo. 输入。因此，阅读结果时应区分纯 RGB 快系统与具有额外空间信息的完整系统。Point-goal 中的坐标也是任务条件的一部分。依据见 §3、§5、Tables 1–2。

**历史：**中心记忆保存带位姿戳的历史图像。快系统对历史进行时空采样，论文示例最多使用 20 帧；慢系统依据候选 frontier 的空间位置与观察朝向，选择能够代表该候选区域的历史图像，并结合占据地图、已探索区域及目标线索决策。这里既有显式的图像／空间记忆，也有论文提到的语言模型 KV cache，两者承担不同作用：前者保存环境经历，后者复用 Transformer 中间计算。不能把“20 帧输入上限”理解为完整慢系统只保留 20 帧，或整个程序具有固定内存占用。依据见 §3、Fig. 1。

**快慢系统协作：**慢系统首先结合任务、当前观测、历史图像及候选前沿进行分析。目标已经出现于当前或历史视野时，模型根据图像与相机位姿预测目标的空间坐标；目标尚未出现时，选择与目标语义相关的探索位置，例如寻找电视时优先考虑客厅方向。随后将子目标交给快系统，以 Point-goal 形式执行。快系统持续根据新视觉观测更新航点，处理子目标途中出现的障碍，并调整最终接近目标的位置与朝向。Fig. 1 中多处 VLM 共享参数；两个训练阶段按离散／连续输出划分，不能对应成两个独立模型的分别训练。论文使用显式 CoT 表达慢系统的分析，但没有详细给出完整的 CoT 标注生产流程、单独的慢系统损失或精确的调用频率规则。依据见 §3、Figs. 1–2、§4.3。

**论文与公开代码的区别：**截至 2026-10-15 核对的官方 `main` 分支，纯视觉 OVON 入口的 `MAX_HISTORY_FRAMES=20`、`NUM_CURRENT_IMAGE=3`；旧观测只保留前视图，超过上限时删除时间间隔最密集的一帧并保留起始帧。当前图像尺寸为 640×569，历史图像按 1/4 缩小，与论文实机的 480×426／120×106 配置不同。每次预测重新打包历史图像与当前图像并调用 `forward()`；该 agent 没有显式将上一步 `past_key_values` 传入下一步，因此这条公开调用路径没有验证论文所述的跨导航步 KV 复用。程序读取仿真位姿用于坐标处理，模型输入与仿真接口提供的信息需要分别检查。[快系统评测代码](https://github.com/amap-cvlab/OmniNav/blob/main/infer_ovon/agent/waypoint_agent_ovon.py)。

公开慢系统脚本默认 `TYPE='A-star'`，运行器调用 `GreedyGeodesicFollower`；另有 `point-goal` 分支调用学习到的快系统。运行器通过 `get_topdown_map_from_sim()` 读取仿真俯视地图，结合可见区域掩码提取前沿，并读取仿真 agent 状态；`point-goal` 执行还使用 `step_filter()`、navmesh 可导航性检查及 `snap_point()`。因此，这份脚本不能直接视为已经实现了论文描述的真实传感器在线建图与完整物理控制链路。慢系统的 `generate()` 和快系统的 `forward()` 使用同一个已加载模型对象，但默认 A-star 入口的局部移动由传统跟随器执行，不能据此宣称默认脚本全程使用学习到的快系统。[慢系统入口](https://github.com/amap-cvlab/OmniNav/blob/main/infer_ovon_slowfast/eval_ovon_slowfast.sh)、[运行器](https://github.com/amap-cvlab/OmniNav/blob/main/infer_ovon_slowfast/run_nav_ovon_omni.py)、[快慢模型调用](https://github.com/amap-cvlab/OmniNav/blob/main/infer_ovon_slowfast/qwen_utils.py)。

**输出：**

- 快系统模型：一次输出未来 5 个航点，每个航点为 `(x, y, sinθ, cosθ, c)`。位置采用当前机器人视角下的局部平面坐标；正余弦表示朝向，避免角度在 ±π 处的不连续；`c` 表示到达／完成。`H=5` 表示航点数量，论文 `S=5` 表示 Flow Matching 推理积分步数，两者是不同参数。
- 慢系统模型：输出分析文字、探索子目标或已发现目标的坐标，并将其交给局部导航环节。分析文本是可见的模型输出，不等于已经证明其内容忠实反映了全部内部决策过程。
- 模拟执行：公开纯视觉 OVON agent 取预测序列的第一个航点，转换成距离与朝向后执行 `GO_TOWARD_POINT`，随后重新观察、预测；到达条件触发时发送停止。Flow 分支要求 5 个到达预测均大于 0.5 才触发该实现中的完成判断，另有最大步数与长时间无进展时的提前停止处理。这些阈值属于公开实现配置。
- 实机执行：论文将预测航点交给机载速度控制模块，结合当前速度与最大加速度生成候选速度并选择可接近航点的速度。模型输出航点，底层速度控制负责实际运动。依据见 §3、式 (1)、§5 的 Real-world deployment；实现依据见上述快系统评测代码。

**训练：**以预训练 Qwen2.5-VL-3B-Instruct 为起点，主要采用离线监督与示范轨迹学习。Point-goal 使用 CityWalker 第一人称行走视频，并通过 DPVO 恢复相机位姿；Instruction-goal 使用 Matterport3D 中的 R2R／RxR 指令与轨迹；Object-goal 在 HM3D 中采样起点和目标类别，通过最短路径导航生成示范；带前沿探索的样本记录探索图像、候选前沿及任务，数据生成策略偏向较短路径并加入有限随机性。通用数据包括 MAmmoTH-VL、RefCOCO 系列、Objects365，以及 ScanQA 和转换成问答形式的 R2R-EnvDrop。每个导航状态以观测和任务为输入，以后续示范动作或航点为监督；三维位姿先转到当前相机局部坐标系，再投影成平面位置、朝向及到达标志。依据见 §4.1–§4.2、Fig. 3。

第一阶段用自回归目标预测离散变量，包括导航动作块、通用视觉语言答案、具身问答和定位结果，建立语义与动作对齐。第二阶段接入 Flow Matching 策略头，监督连续航点，并继续使用第一阶段离散数据的 20%，以保留基础 VLM 能力；论文未说明每个 batch 必须按固定 80:20 比例组成。连续坐标采用 min-max 归一化。该训练路线没有报告 PPO／GRPO 等在线奖励优化阶段，不能将其主要训练过程概括为强化学习。依据见 §4.3。

公开 `train_demo_flow.sh` 使用 BF16、`train_type=full`、`freeze_vit=true`、`freeze_llm=false`、`freeze_aligner=false`，即冻结视觉编码器、更新语言模型与对齐层，并训练策略头。示例学习率为 8.62×10⁻⁶、1 epoch、每设备 batch size=2、梯度累积 1、最大序列长度 8192、warmup ratio=0.05、余弦学习率和 FlashAttention。它从示例 OmniNav Flow 路径加载权重，不能直接当成论文第二阶段全部正式实验的统一超参数。README 要求 Flow 数据包含 `norm` 统计量，旧的 `waypoint_train_demo.json` 不能直接用于 Flow 训练。另一个 `run_train_demo.sh` 对应 Action Former 分支，也不能直接等同于论文第一阶段自回归训练配置。[Flow 训练示例](https://github.com/amap-cvlab/OmniNav/blob/main/train_code/train_demo_flow.sh)、[Action Former 示例](https://github.com/amap-cvlab/OmniNav/blob/main/train_code/run_train_demo.sh)、[官方说明](https://github.com/amap-cvlab/OmniNav#-training)。

**Flow Matching 与监督目标：**VLM 的融合特征记为 `O`，处理后的真实航点序列记为 `W`，随机噪声为 `ε`，采样时间为 `τ`。训练输入为 `W_τ = (1−τ)ε + τW`；策略头通过自注意力协调航点序列，通过交叉注意力读取 `O`。官方代码进一步对相邻航点做差分、对朝向使用正余弦，并进行归一化；Flow 分支用 `mean(||v_θ(O, W_τ, τ) − (W−ε)||²)` 监督速度场。训练时采样噪声与一个时间位置计算损失；推理时从噪声出发，多次积分生成整段航点。第二阶段保留离散监督，使骨干继续接受语言与视觉任务约束。依据见 §3、式 (1)–(4)、§4.3 及[官方模型实现](https://github.com/amap-cvlab/OmniNav/blob/main/train_code/transformers-main/src/transformers/models/qwen2_5_vl/modeling_qwen2_5_vl.py)。

**公式与代码的差异：**论文式 (2) 定义 `τ=0` 为噪声、`τ=1` 为真实航点，式 (3) 却将目标残差写成 `ε−W`，式 (4) 又采用加法推进；按该时间方向，三式的符号存在不一致。官方代码使用 `velocity = delta_waypoints - noise`，与从噪声到目标的正向积分一致，本笔记按代码解释更新方向。另一个配置差别是，论文报告 `S=5`，而公开训练目录中 `FlowmatchingActionHeadConfig` 的 `num_inference_timesteps` 默认值为 10；复现应核对实际导入的模型实现与运行配置。上述两点均不应通过把“5 个航点”和“5 次积分”混为一谈来解释。

**训练算力与推理部署：**论文 §4.3 明确报告第一阶段使用 **96 张 NVIDIA H20，训练 120 小时**，第二阶段使用 **64 张 H20，训练 48 小时**。按卡数与时长计算分别为 11,520 和 3,072 H20 GPU·小时，总计 **14,592 H20 GPU·小时**；两阶段顺序运行的报告时长合计约 7 天。这是以预训练 VLM 为起点的两阶段训练用量，不包含基座模型原始预训练，也不能视为数据生成、所有调参和全部消融实验的项目总成本。论文没有报告各阶段完整的全局 batch size、最低训练显存或最少 GPU 数。

真机实验将 **快系统的 VLM 与策略头**部署于 RTX 3090 云服务器：最多 20 张 120×106 历史前视图，当前输入为 480×426 三视图，论文报告运行超过 5 Hz。文中未给出峰值显存、分项网络时延或完整慢系统的实机控制频率。作者明确说明，完整慢系统的物理部署仍需额外的 LiDAR／深度估计集成与时延优化；3090 上的频率不能扩展为完整快慢系统已经在相同配置下达到该速度。依据见 §5 的 Real-world deployment、Fig. 4。

**评测：**R2R-CE 与 RxR-CE 的 Val-Unseen 使用纯视觉快系统。Table 1 中，OmniNav 在 R2R-CE 上 **NE=3.74、SR=69.5%、SPL=66.1%**，在 RxR-CE 上 **NE=3.77、SR=73.6%、SPL=62.0%**。无 policy-head 的变体在两个基准上的 SR／SPL 分别为 59.8%／57.5% 与 64.1%／53.9%。比较不同论文时需同时检查表中的三视角／单视角、深度、里程计及训练数据条件。

HM3D-OVON 的 Table 2 分别报告 Val-Seen、Val-Seen-Synonyms 与 Val-Unseen。纯 RGB 快系统的 SR／SPL 依次为 **46.6%／23.3%、50.4%／28.5%、43.5%／27.3%**；加入慢系统与 CoT 的 OmniNav* 依次为 **56.1%／30.0%、68.6%／38.8%、59.2%／33.2%**，该完整系统同时使用深度与里程计。表中 MTU3D 的 Val-Unseen SR 为 40.8%，完整 OmniNav* 高出 18.4 个百分点；这里应使用百分点描述绝对 SR 差。CityWalker 的 Point-goal 比较中，正文报告 MAOE 为 OmniNav 11.53%、CityWalker 15.23%，该项误差指标应与导航成功率分别理解。依据见 §5、Tables 1–2。

**消融与配置说明：**Table 3 在 HM3D-OVON Val-Unseen 上采用递增配置：基础变体 SR／SPL=35.3%／22.1%；加入 policy-head 后为 43.5%／27.3%；再加入慢系统为 55.9%／30.7%；再加入通用数据为 57.7%／32.9%；最终加入 CoT 为 59.2%／33.2%。相邻配置的 SR 增量分别是 8.2、12.4、1.8 和 1.5 个百分点。该表支持这些组件在相应已有配置上的增益；其中加入慢系统伴随地图、深度和里程计，不能把全部增益归因于单一的文字推理机制，也不能将该递增表解释为完整的独立因素实验。

附录 A.1 的 Table 4 单独检查三类辅助数据：均不加入时为 55.9%；去掉 Embodied Q&A、去掉 Grounding／Referring、去掉 General MLLM 数据时分别为 56.5%、56.7%、57.0%；全部加入时为 57.7%。作者通过案例将具身问答与定位数据的收益联系到小物体识别，将通用视觉语言数据的收益联系到不规则物体识别；这些案例提供解释线索，不等于已经排除所有其他训练因素。Table 5 中，无额外辅助数据时 3B／7B 的 SR 为 55.9%／57.2%，加入后为 57.7%／57.9%。在该实验配置下，辅助数据缩小了两种模型规模的差距，尚不能推出任意任务上扩大模型都无益。依据见 §5、Table 3、附录 A.1、Tables 4–5。

**局限与复现边界：**作者指出，完整慢系统的真实机器人部署及其时延—频率权衡仍需进一步研究；附录也报告 carpet、clothes、mirrors 等复杂外观目标的识别仍不稳定，并因算力限制没有开展系统的数据质量、数据配比与模型规模联合扩展研究。就现有证据而言，快慢系统收益应连同其传感器和地图条件一起理解；公开脚本的仿真地图、传统跟随器和位置过滤也需要在复现报告中说明。论文尚未给出足以独立还原全部训练配方的细节，尤其是各类数据的完整采样计划、慢系统 CoT 标注生成和全部正式实验超参数。前两项局限来自作者说明，后面的复现边界来自对论文与代码披露范围的核对。
