# 系统组织架构：新版方法分类 PPT 内容

本文件仅提供这一一级分支的 4 张方法正文页与 1 张可选比较页。二级类别按《一级分支分类.md》保持为“分层与模块化协作”“多能力统一联合建模”；每篇论文是类别内的实现例子，不作为独立方法类别。下面“屏幕内容”可直接入页；“讲者备注”用于扩展解释。

## 页面 A1｜分层与模块化协作：把任务决策交给高层，把移动交给执行器

### 屏幕内容

**要解决的问题**：语言任务涉及搜索、判断和移动，单一决策频率与输出形式难以兼顾。

**核心思路**：通过程序、工具参数或空间子目标连接高层决策与低层执行。

**四步闭环**

1. 读取指令、当前观测与任务进度。
2. 高层选择工具、技能或下一子目标。
3. 专门模块完成感知、规划与局部运动。
4. 执行状态和新观测返回高层，继续决策。

| 同一方法范式 | 高层输出 | 执行端如何接住 |
|---|---|---|
| TANGO：程序编排 | 由原语调用组成的伪程序 | 解释器依次调用感知、探索与 PointNav 模块 |
| SuperNav：智能体工具循环 | 工具调用、所选视角与图像点 | 几何式或学习式执行器完成移动，并返回诊断 |
| OmniNav：快慢协作 | 目标／探索子目标的空间坐标 | 快系统生成短程航点，底层控制器执行 |

**收益**：分工明确、接口便于替换、可复用已有模块。

**代价**：接口误差会传递；高层调用与反馈管理增加系统复杂度。

### 讲者备注（约 220 字）

这一类的共同点是决策层与执行层通过明确接口协作。TANGO 先把请求组织成可解释的程序，再由解释器调用具体模块；SuperNav 更强调每轮查看工具返回的视觉与诊断信息，继续调用工具；OmniNav 则让慢系统选择空间子目标，快系统持续更新局部航点。它们都可以处理多种任务，因此“分层”不能等同于“单任务”。优势是可以复用成熟执行器，定位错误也较方便；局限是模块间可能存在坐标、语义和状态不一致，高层看到的证据也可能滞后。这里概括的是组织方式，不能据此推断训练算力必然较小。

### 来源与定位

- 新版分类：`一级分支分类.md`，系统组织架构／分层与模块化协作。
- TANGO：`03_大模型规划与工具调用/read-Tango.md`；本地论文 `03_大模型规划与工具调用/2025_CVPR_TANGO.pdf`，§3、§3.1；Fig. 2 程序生成与解释，Fig. 3 原语模块；PDF 页序 3–5。

## 页面 A2｜代表实现 OmniNav：慢系统决定去哪里，快系统决定怎么走

### 屏幕内容

**同类代表**：OmniNav；关键接口是 **Point-goal 子目标**。

**输入 → 输出的四步机制**

1. **建立依据**：任务＋当前 RGB＋带位姿的历史图像；完整系统另用深度与里程计维护地图和前沿。
2. **慢系统选子目标**：已见目标则定位；未见目标则选择相关探索前沿。
3. **快系统生成航点**：共享 VLM 融合任务、视觉与坐标；Flow Matching 策略头产生短程连续航点序列。
4. **执行后再观察**：底层运动控制跟随航点，持续更新观测；必要时重新选择子目标。

**以“寻找电视”为例**

未知电视位置 → 根据场景语义优先探索客厅方向 → 向前沿移动 → 观察到电视后改为接近目标。

**与同类区别**：TANGO 输出程序；SuperNav 输出工具调用和图像点；OmniNav 用共享骨干衔接全局选择与局部航点生成。

**能力边界**：快慢系统共享参数；完整系统与纯 RGB 快系统的传感器条件不同。

### 讲者备注（约 240 字）

OmniNav 说明了分层并不必然意味着使用两个独立大模型。它的快慢系统共享视觉语言骨干，区别主要在决策尺度与输出接口。慢系统利用任务、历史和空间候选判断下一步去哪，快系统把坐标子目标变成可执行的航点序列；航点还需要底层控制器转换成运动。论文两阶段训练分别处理离散输出与连续航点，不能解释成分别训练慢、快两个独立模型。报告效果时应区分纯视觉快系统和增加深度、里程计的完整系统；实机超过 5 Hz 的披露主要对应快系统，不能直接外推到完整快慢系统。该例强调子目标协作，不把成功归因于某一个模块。

### 来源与定位

- 阅读笔记：`05_视觉语言动作决策与视频记忆/read-OmniNav.md`，“快慢系统协作”“Flow Matching 与监督目标”“训练算力与推理部署”。
- 原论文：§3、Fig. 1 总体结构；Fig. 2 慢系统示例；式 (1)–(4) 航点与 Flow Matching；§4.3 两阶段训练；§5、Table 2 的传感器条件；§5 Real-world deployment 的部署范围。

## 页面 B1｜多能力统一联合建模：让相关能力共享表示与决策接口

### 屏幕内容

**要解决的问题**：规划、定位与探索分开学习，容易出现目标理解不一致与能力衔接困难。

**核心思路**：在共享模型、表示或输出空间中联合学习相互关联的能力。

**四步机制**

1. 将目标、观测与历史转换成可共同处理的表示。
2. 共享网络融合语义、空间与任务信息。
3. 用统一接口输出计划、目标、航点、动作或候选评分。
4. 结合多能力数据训练，并用执行反馈更新下一次决策。

| 论文例子 | 统一的是什么 | 保留的执行边界 |
|---|---|---|
| D3D-VLP | 计划→三维目标定位→航点选择的结构化生成 | 航点预测器与动作控制器 |
| Uni-NaVid | 四种任务共享 RGB 视频、任务文本与输出接口 | 短期离散动作由机器人底层执行 |
| MTU3D | 对象定位与前沿探索进入同一候选评分空间 | 轨迹规划器负责前往候选位置 |

**收益**：减少表示割裂，支持能力迁移与统一决策。

**代价**：依赖数据覆盖与任务对齐；统一模型仍可能保留专门模块。

### 讲者备注（约 235 字）

这一类统一的对象并不相同。D3D-VLP 让规划、三维定位与导航处于同一自回归序列，并共享环境和进度记忆；Uni-NaVid 让视觉语言导航、物体导航、具身问答和人物跟随共用视频语言接口，通过标记切换动作或文字；MTU3D 则把已观察对象与待探索前沿一起打分，从而决定现在接近目标，还是继续找目标。这里的“统一”描述学习与决策接口，不能泛化为从传感器到电机的完全端到端系统。三者仍保留不同程度的执行模块。多任务训练和分层协作可以同时存在，一级归属依据论文最突出的主要贡献，而不是排除其他属性。

### 来源与定位

- D3D-VLP：`04_三维空间表征与目标推理/read-D3D.md`；§3.1–§3.3、Figs. 2–3。
- Uni-NaVid：`05_视觉语言动作决策与视频记忆/read-UniNavid.md`；§III、§IV-A–C、Fig. 2；§V 数据与训练；Table X 与 Fig. 8 的记忆和多任务实验。
- MTU3D：`04_三维空间表征与目标推理/read-MTU.md`；§3.1–§3.4；Fig. 3 在线对象记忆、统一对象／前沿评分与执行闭环。

## 页面 B2｜代表实现 D3D-VLP：把计划、目标与航点连成可更新的决策链

### 屏幕内容

**同类代表**：D3D-VLP；关键接口是 **动态三维 CoT 序列**。

**输入 → 输出的四步机制**

1. **累积三维证据**：RGB-D＋位姿更新多层次 3D Memory，形成图像块、对象与区域 tokens。
2. **对齐任务和空间**：指令、三维 tokens、候选航点与历史 CoT 共同进入 3D-VLM。
3. **联合产生决策**：生成后续计划，定位三维目标，再选择航点；需要时生成回答。
4. **反馈并重规划**：控制器执行航点，已走轨迹和完成进度进入 CoT Memory，支持后续调整。

**训练如何支撑统一**

混合全标注与部分标注样本 → 生成完整决策序列 → 只对已有标注计算损失（SLFS）。

**与同类区别**：Uni-NaVid 统一任务与动作接口；MTU3D 统一对象／前沿评分；D3D-VLP 显式串联计划、三维定位与导航。

**收益与边界**：决策链可检查、进度可更新；同时依赖三维感知质量、可通行航点与训练监督。

### 讲者备注（约 235 字）

D3D-VLP 的“统一”发生在决策链内部：模型不能只写一个与执行脱节的静态计划，还要结合三维证据定位目标并决定下一航点。执行以后，历史计划、已定位目标和经过的轨迹被重新放回上下文，因此后续决策可以感知任务进度。三维记忆与 CoT 记忆作用不同，前者描述环境，后者描述决策和进展。SLFS 使只有导航标注或只有定位标注的样本也能参与共享模型训练，但并不等于缺失的中间步骤都有真实标签。该方法仍需要候选航点与底层控制，三维建图或定位发生错误时，统一生成本身不能自动保证安全与正确。

### 来源与定位

- 阅读笔记：`04_三维空间表征与目标推理/read-D3D.md`，三维感知／统一决策／协同训练。
- 原论文：`04_三维空间表征与目标推理/2026_CVPR_D3D-VLP.pdf`；§3.1 多层次三维感知，§3.2 动态三维 CoT，§3.3 SLFS；Fig. 2 总框架，Fig. 3 统一自回归序列及 CoT Memory；PDF 页序 3–5。

## 页面 C｜可选比较：组织分工与统一建模是两个不同观察角度

### 屏幕内容

| 比较项 | 分层与模块化协作 | 多能力统一联合建模 |
|---|---|---|
| 主要问题 | 不同层级怎样协同完成任务 | 不同能力怎样共享理解与学习 |
| 重点设计 | 工具接口、子目标、执行反馈 | 共享表示、统一输出、联合监督 |
| 典型接口 | 程序调用／图像点／空间子目标 | 结构化序列／任务标记／候选评分 |
| 主要风险 | 模块衔接与反馈误差 | 数据覆盖、任务对齐与感知误差 |
| 代表文献 | TANGO、SuperNav、OmniNav | D3D-VLP、Uni-NaVid、MTU3D |

**两类可以共存**：OmniNav 同时统一多种目标类型；D3D-VLP 与 MTU3D 同时保留独立的执行模块。

**分类依据是主要贡献，不是任务数量、二维／三维或训练算力。**

### 讲者备注（约 190 字）

这张比较用于解释分类口径。分层协作关注系统内部如何分工，统一建模关注不同能力如何共享表示和训练，两者不是严格互斥的系统属性。把每篇文章放在一个主要分支，是为了讲清它最突出的研究贡献，并不意味着其他方法特征不存在。因此，OmniNav 虽然有统一多任务骨干，仍以快慢协作为这里的主线；MTU3D 虽然有独立规划器，仍以对象定位和探索统一为主线。二维与三维属于表征形式，算力属于资源条件，均应在相应页面单独注明，不能替代方法分类。
